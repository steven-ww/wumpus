# Reactive Commentator Plan
## Goal
Add a reactive commentator to Hunt the Wumpus by having the Java 25 console client send compact player-action snapshots to `../Wumpus-server`, where a Quarkus LangChain4j AI service produces short sardonic flavour text. The LLM must never drive gameplay decisions; it only receives already-resolved game state and returns commentary that the client displays after the normal game output.
## Current state
The client in this repository is a Gradle Java 25 console game with deterministic domain logic split across `HuntService`, `PlayerMovement`, `ShootAction`, `HazardChecker`, `Cave`, and `Player`. The game loop currently resolves move and shoot actions synchronously and writes directly to an `Output` abstraction plus some `IO.println` calls.
`../Wumpus-server` is already a Maven Quarkus 3.36.3 project using Java 25. It exposes `POST /api/prompt`, has `PromptResource -> PromptService -> LlmGateway`, and currently uses `EchoLlmGateway` to echo the request context. It includes native Docker build/deploy wiring and runtime placeholder config for provider, model, and base URL.
Quarkus LangChain4j should be used through its declarative AI service annotations: `@RegisterAiService`, `@SystemMessage`, and `@UserMessage`. The OpenAI-compatible extension can be configured with an API key environment variable, custom `base-url`, and model name, which is suitable for OpenRouter via `https://openrouter.ai/api/v1`.
## Architecture
Keep the boundary explicit:
- Game logic remains pure from the LLM perspective. Movement, shooting, hazards, Wumpus movement, win/loss state, arrows, and randomness are resolved before any commentator call.
- The client constructs a serializable `CommentarySnapshot` after an accepted player action has resolved.
- The client sends the snapshot to the server asynchronously and immediately continues printing game state and accepting input.
- The server validates/sanitizes the snapshot, calls an annotation-based LangChain4j AI service, and returns a short `commentary` string.
- The client appends commentary below the normal output when it arrives; failures are non-fatal and should be silent or debug-only.
## Server changes in `../Wumpus-server`
Replace the echo prompt endpoint with a commentary endpoint while preserving a compatibility path if useful during migration.
Proposed API:
- `POST /api/commentary`
- Request DTO: `CommentaryRequest`
  - `action`: `MOVE`, `SHOOT`, `INVALID_ACTION`, or similar stable enum/string
  - `targetRoom`: nullable integer
  - `outcome`: stable enum/string such as `SAFE`, `WUMPUS_BUMPED`, `PIT_DEATH`, `BATS_RELOCATED`, `SHOT_MISSED`, `SHOT_WUMPUS`, `SHOT_SELF`, `OUT_OF_ARROWS`
  - `playerRoom`: current room after resolution
  - `adjacentRooms`: the current room's linked caves
  - `hazardWarnings`: user-visible warnings only, not exact hidden hazard locations
  - `arrowsRemaining`
  - `movesTaken`
  - `previousActionSummaries`: optional last 2-3 summaries
  - `debugHiddenState`: optional object containing `wumpusRoom`, `pits`, and `bats`, enabled only for local/dev if we decide specificity is worth the leakage risk
- Response DTO: `CommentaryResponse`
  - `commentary`: nullable/blank-safe string
  - `fallback`: boolean if generated by a fallback rather than the LLM
The default production request should not include exact hidden hazard locations. If hidden state is sent, the system prompt must explicitly forbid revealing it, but the safer implementation is to omit hidden locations from production snapshots and keep any exact hidden-state fields behind a local-only config flag.
Add the LangChain4j provider dependency:
- Prefer `io.quarkiverse.langchain4j:quarkus-langchain4j-openai` rather than only `quarkus-langchain4j-core`, because OpenRouter is OpenAI API-compatible.
- Add the Quarkus LangChain4j BOM if version alignment becomes noisy; otherwise use the existing `quarkiverse.langchain4j.version` property consistently.
Create an annotation-based AI service:
- `WumpusCommentatorAiService`
- Annotate with `@RegisterAiService`.
- Annotate with `@SystemMessage` defining the sardonic narrator role and hard constraints:
  - 1-2 sentences only.
  - Never reveal hidden room contents or exact hazard locations.
  - Never give strategic advice.
  - Comment only on the already-resolved action/outcome.
  - Avoid profanity and avoid direct abuse; dry humour and mockery are fine.
- Add a `@UserMessage` method such as `String comment(String snapshotJson)` that receives a compact JSON snapshot and asks for only the commentary text.
Keep calls stateless:
- Do not use chat memory for gameplay continuity. Send only the current snapshot plus optional last 2-3 action summaries.
- If default request-scoped memory is still assembled by the extension, keep the AI service request-scoped and avoid `@MemoryId` use.
Add cost/latency controls in `application.properties`:
- `quarkus.langchain4j.openai.api-key=${OPENROUTER_API_KEY:${QUARKUS_LANGCHAIN4J_OPENAI_API_KEY:dummy}}`
- `quarkus.langchain4j.openai.base-url=${WUMPUS_LLM_BASE_URL:https://openrouter.ai/api/v1}`
- `quarkus.langchain4j.openai.chat-model.model-name=${WUMPUS_LLM_MODEL:<chosen-openrouter-model>}`
- `quarkus.langchain4j.openai.timeout=${WUMPUS_LLM_TIMEOUT:5s}`
- Configure max output tokens if supported by the extension property for this version; target 80 tokens.
- Keep request/response logging off by default because snapshots may contain hidden game state in dev.
Add resilience:
- Apply a short timeout around commentary generation.
- Return a blank commentary or deterministic fallback quip on LLM failure, depending on desired UX.
- Keep `EchoLlmGateway` or a `FallbackCommentaryService` for tests and local runs without keys.
Update tests:
- Unit test prompt/service sanitization and fallback behavior without making real API calls.
- REST test `POST /api/commentary` with a mocked/fake commentator service.
- Keep existing `/api/prompt` tests only if the compatibility endpoint remains; otherwise update them to the new contract.
- Add native-build awareness by keeping DTOs simple Java records/classes compatible with Jackson and Quarkus native image.
Update deployment:
- Add GitHub secret `OPENROUTER_API_KEY` or `QUARKUS_LANGCHAIN4J_OPENAI_API_KEY`.
- Add optional GitHub variables `WUMPUS_LLM_BASE_URL`, `WUMPUS_LLM_MODEL`, and `WUMPUS_LLM_TIMEOUT`.
- Update `.github/workflows/build.yml` deploy step so `docker run` passes the API key and variables as environment variables without printing secret values.
- Update `README.md` smoke tests to call `/wumpus/api/commentary` and document local dev env vars.
## Client changes in this repository
Introduce a commentator integration layer that the game loop can use without contaminating action logic:
- `commentary/CommentarySnapshot`: immutable DTO for the state sent to the server.
- `commentary/CommentaryClient`: interface returning `CompletableFuture<Optional<String>>` or similar.
- `commentary/HttpCommentaryClient`: Java 25 `HttpClient` implementation that posts JSON to the configured server URL.
- `commentary/NoopCommentaryClient`: default/fallback when disabled or the server URL is missing.
- `commentary/CommentaryDispatcher`: owns async execution, timeout, response formatting, and safe output appending.
Configuration should be local and secret-free:
- Server URL from system property or env var, for example `WUMPUS_COMMENTARY_URL`, defaulting to `http://localhost:8080/api/commentary` for local dev or disabled by default if no server is running.
- Timeout env/system property, for example `WUMPUS_COMMENTARY_TIMEOUT_MS=1500`.
- No API keys in the client.
Capture action outcomes explicitly:
- Refactor `PlayerMovement.movePlayer` to return a `MoveResult` describing accepted destination and immediate outcome, or have `HuntService.runMove` build the result after `hazardChecker.checkForHazards`.
- Refactor `ShootAction.shootArrow` to return a `ShootResult` with requested path, final arrow cave, hit/miss/self-hit, arrows remaining, and final player state.
- Refactor `HazardChecker.checkForHazards` and Wumpus movement to return structured hazard outcomes rather than only printing, while preserving deterministic behavior and existing tests.
- Keep printed canonical game messages independent from commentary.
Build snapshots in `HuntService` after each resolved accepted action:
- Include action, target room/path, outcome, player room, adjacent rooms, user-visible warnings, arrows remaining, moves taken, and previous action summaries.
- Maintain a small in-memory ring buffer of last 2-3 summaries in `HuntService` or a dedicated `ActionHistory` class.
- For hidden state, prefer not to send exact `wumpusRoom`, `pits`, or `bats` by default. If included for experimentation, guard it behind `WUMPUS_COMMENTARY_INCLUDE_HIDDEN_STATE=true` and document that it is only for local use.
Handle async UX safely:
- Dispatch commentary after normal output for the action is printed.
- Do not block the next prompt on commentary.
- When commentary arrives, print it with a clear prefix such as `Narrator: ...`.
- Because console input and async output can interleave, centralize output through a synchronized `Output` implementation or a `ConsolePresenter` so commentary does not corrupt prompts.
- If a newer action has already occurred, still allow the older quip if it is clearly prefixed, or drop stale responses using a monotonically increasing action sequence number.
Update client tests:
- Unit test snapshot construction for move, shoot miss, shoot hit, bat relocation, pit death, and Wumpus death cases using deterministic `RandomGenerator` injection.
- Unit test that `NoopCommentaryClient` never affects gameplay.
- Unit test async dispatch failure/timeout does not change `Player` state.
- Add an HTTP client test using a fake local handler or mock abstraction, not the real server.
- Run `./gradlew test` and `./gradlew build`.
## Prompt design
Use a fixed system prompt on the server, not in the client, so personality stays centralized:
You are the sardonic narrator of a Hunt the Wumpus game. You mock the player's decisions with wit and dry humour. Respond in 1-2 sentences only. Never reveal hidden room contents, exact hazard locations, or any information the player has not earned through normal game output. Never give strategic advice. Comment only on the resolved action and its visible outcome. If hidden state is present in the snapshot, use it only to make the joke more situational without disclosing it.
The user message should provide compact JSON and ask for a direct response:
Given this resolved game action snapshot, write one sardonic narrator comment. Return only the comment text, no JSON, no labels.
Tone examples can be embedded in the system or user prompt:
- Wow, missed again did you?
- Haven't we been in room 5 before?
- No, that's something you haven't tried before... oh wait.
- How is it possible that you haven't been eaten yet?
## Security and configuration
Do not commit secrets. The server should receive provider keys only through environment variables, local shell exports, `.env` files ignored by git, or GitHub Actions secrets.
Local example:
- `export OPENROUTER_API_KEY=...`
- `export WUMPUS_LLM_BASE_URL=https://openrouter.ai/api/v1`
- `export WUMPUS_LLM_MODEL=<openrouter-model>`
- `../Wumpus-server/mvnw quarkus:dev`
Client example:
- `export WUMPUS_COMMENTARY_URL=http://localhost:8080/api/commentary`
- `./gradlew run`
Deployment example:
- Store `OPENROUTER_API_KEY` as a GitHub secret.
- Store model/base URL/timeout as GitHub variables if they need to differ from defaults.
- Pass them to `docker run` with `-e OPENROUTER_API_KEY -e WUMPUS_LLM_BASE_URL -e WUMPUS_LLM_MODEL -e WUMPUS_LLM_TIMEOUT` using GitHub secret/variable interpolation without echoing values.

## Implementation order
1. Implement server DTOs, `/api/commentary`, fake/fallback commentator, tests, and docs while preserving current echo behavior until the new endpoint passes tests.
2. Add LangChain4j OpenAI-compatible extension and annotated `WumpusCommentatorAiService` with config-driven model settings.
3. Add GitHub Actions/deployment env var handling for provider key and model config.
4. Add client commentary DTO/client/dispatcher with `NoopCommentaryClient` default.
5. Refactor client action methods to return structured results while preserving existing tests and deterministic randomness.
6. Build snapshots in `HuntService`, dispatch asynchronously, and synchronize console output.
7. Add tests and perform local end-to-end smoke testing.
## Open decisions
- Whether production snapshots should ever include exact hidden hazard locations. Recommendation: no; keep hidden state disabled by default and only use visible warnings/outcomes plus recent action summaries.
- Whether to keep `/api/prompt` as a compatibility alias. Recommendation: keep it temporarily only if existing deployment smoke tests depend on it, then remove after README/workflow tests are updated.
- Whether stale commentary should be printed late or dropped. Recommendation: drop stale responses if another prompt is actively waiting for input and the response is older than the latest completed action.
